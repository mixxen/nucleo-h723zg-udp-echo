# W5500 shield UDP echo server

This optional Rust firmware uses the WIZnet W5500 Ethernet shield on the
NUCLEO-H723ZG Arduino headers. It is a separate executable from the native
LAN8742A/RMII firmware, so the onboard Ethernet peripheral and RJ45 connector
are not initialized.

## Two W5500 implementations

The repository deliberately provides two ways to use the same shield:

| Executable | SPI data | Network implementation |
|---|---|---|
| `nucleo-h723zg-w5500-udp-echo` | Complete raw Ethernet frames | Embassy implements DHCP, IPv4, ICMP, and UDP |
| `nucleo-h723zg-w5500-offload-udp-echo` | Decoded UDP payloads and socket commands | W5500 hardware implements the network protocols |

They are separate firmware images; only one runs at a time.

## MACRAW architecture

```text
Ethernet cable -> W5500 MAC/PHY -> SPI1 -> embassy-net-wiznet
                                             |
                                      raw Ethernet frames
                                             |
                          embassy-net -> DHCP + UDP port 7
```

The W5500 contains its own Ethernet MAC, PHY, and packet memory. In this
application it operates in MACRAW mode: it transfers complete Ethernet frames
to the STM32 over SPI, while Embassy implements ARP, DHCP, IPv4, ICMP, and
UDP. This lets the shield reuse the same network supervisor and UDP echo task
as the native-Ethernet firmware.

Embassy tasks run cooperatively without an RTOS or heap. A short SPI transfer
is blocking; waits for packets and timers are asynchronous. The firmware
polls the W5500 every millisecond, so the shield's optional INT-to-D2
connection is not required.

## Hardware-offload architecture

```text
Ethernet cable -> W5500 MAC/PHY + IPv4/UDP engine
                                      |
                          hardware socket 0: DHCP
                          hardware socket 1: UDP port 7
                                      |
                               SPI registers +
                            decoded UDP payloads
                                      |
                                    STM32
                              receive -> send
```

This smaller version removes `embassy-net` from the data path. The STM32 asks
the W5500 for a decoded datagram consisting of its source address, source port,
length, and payload. It writes the same payload into the W5500 transmit buffer
and issues a SEND command. Ethernet framing, ARP, IPv4, and UDP checksums stay
inside the chip.

The tradeoff is flexibility. The W5500 exposes only eight hardware sockets,
and its offload engine—not Rust—defines their protocol behavior. In
particular, the chip does not complete a SEND operation for a zero-byte UDP
payload. This version safely discards such a datagram and continues serving
later traffic; the MACRAW/Embassy version can echo it.

## Wiring used on NUCLEO-H723ZG

The shield plugs directly into the Arduino-compatible headers:

| Shield signal | Arduino pin | STM32 pin |
|---|---|---|
| SCLK | D13 | PA5 / SPI1_SCK |
| MISO | D12 | PA6 / SPI1_MISO |
| MOSI | D11 | PB5 / SPI1_MOSI |
| W5500 chip select | D10 | PD14 / GPIO |
| Reset | RESET | Board NRST |

The SD-card chip select on D4 is unused. MACRAW retains its 20 MHz SPI request.
The ordinary hardware-offload build requests 50 MHz. Its 520 MHz performance
build derives a dedicated 80 MHz SPI1 kernel clock from PLL2-P and divides it
to a validated 40 MHz. Independent 50 MHz SPI and the earlier approximately
65 MHz configuration obtained no DHCP lease or network response with the
performance CPU clock. The firmware uses locally administered MAC address
`02-00-00-00-55-00`, deliberately different from the native interface.

## Build and flash

Connect the ST-LINK USB cable and connect Ethernet only to the W5500 shield.
From the repository root, build a signed W5500 image and flash MCUboot plus the
application:

```powershell
powershell -ExecutionPolicy Bypass -File .\Rust\tools\build-signed.ps1 `
    -Version 0.2.4 `
    -W5500

powershell -ExecutionPolicy Bypass -File .\Rust\tools\flash.ps1 `
    -SkipBuild `
    -W5500
```

For a later build, choose a version appropriate for that release. The signed
output is `Rust\artifacts\firmware-w5500-signed.bin`.

You can also perform both operations with one command:

```powershell
powershell -ExecutionPolicy Bypass -File .\Rust\tools\flash.ps1 `
    -Version 0.2.4 `
    -W5500
```

### Build the hardware-offload version

Use `-W5500Offload` instead of `-W5500`; this creates a distinct artifact and
does not replace the MACRAW source or build output:

```powershell
powershell -ExecutionPolicy Bypass -File .\Rust\tools\flash.ps1 `
    -Version 0.2.6 `
    -W5500Offload
```

The signed output is
`Rust\artifacts\firmware-w5500-offload-signed.bin`.

For the speed-oriented offload image used by the stream trade study:

```powershell
powershell -ExecutionPolicy Bypass -File .\Rust\tools\flash.ps1 `
    -Version 0.4.4 `
    -W5500Offload `
    -Performance
```

This creates `Rust\artifacts\firmware-w5500-offload-performance-signed.bin`.

## Find the address and test UDP echo

Look in the router's DHCP client list for MAC `02-00-00-00-55-00`. Set the
address assigned by your router and run the existing binary acceptance test:

```powershell
$boardIp = "192.168.68.74" # Replace with the current DHCP address.

powershell -ExecutionPolicy Bypass -File .\Rust\tools\udp_echo_test.ps1 `
    -BoardIp $boardIp
```

The program listens on UDP port 7 and sends every datagram back to its actual
source address and port. It also answers ICMP ping after DHCP completes.

For the hardware-offload build, omit the unsupported zero-byte case:

```powershell
powershell -ExecutionPolicy Bypass -File .\Rust\tools\udp_echo_test.ps1 `
    -BoardIp $boardIp `
    -Sizes 1,32,256,1472
```

This small W5500 executable intentionally provides only network supervision
and UDP echo. The native-RMII executable remains the version that provides
SSH management and signed updates over Ethernet.

For a controlled source comparison with a UDP-only native-RMII peer, see
[TRADE_STUDY.md](TRADE_STUDY.md). That study separates device/network
bring-up from the actual echo-server code and provides a repeatable metrics
script.

## Verified board result

On 2026-08-12, the connected W5500 reported its expected chip version at a
20 MHz SPI clock, negotiated link, and obtained `192.168.68.74/22` by DHCP.
The Windows acceptance test sent 1,000 datagrams, cycling through 0, 1, 32,
256, and 1,472-byte payloads; every packet returned byte-for-byte from
`192.168.68.74:7`.

The hardware-offload executable was then independently flashed. It obtained
the same DHCP lease and echoed 1,000 non-empty datagrams across the 1, 32,
256, and 1,472-byte test sizes. Its signed image was about 23 KiB, compared
with about 65 KiB for the MACRAW/Embassy image.

On 2026-08-13, the optimized offload performance image passed binary echo at
1, 100, and 1,472 bytes. Its retained dedicated-40-MHz SPI build was
zero-error from 1 through 14 kHz and first failed at 15 kHz. A longer 14 kHz
trial returned all 420,000 packets in 30 seconds. See
[STREAM_BENCHMARK_REPORT.md](STREAM_BENCHMARK_REPORT.md#w5500-hardware-offload-optimization)
for the staged measurements and DMA assessment.

## DMA assessment

SPI DMA is possible on the STM32H723, but it is not a drop-in optimization for
the current W5500 hardwired-socket application:

- `w5500-ll` already uses W5500 variable-data-length mode, keeping chip select
  asserted across each three-byte command header and its register or payload
  data. The current Embassy SPI object executes those transactions in blocking
  mode without MCU DMA.
- The `w5500-hl` UDP reader/writer API used here is synchronous. Embassy's DMA
  SPI API is asynchronous, so using it properly requires an async high-level
  W5500 path or a carefully tested adapter between the two models.
- An echo cannot start its next W5500 command while the current SPI transfer is
  active. DMA can free MCU cycles during a payload transfer, but it cannot
  overlap another command on the same serial bus or reduce the bytes crossing
  that bus.
- A 100-byte echo performs several short register operations around two
  payload transfers. DMA setup on the 1-9 byte operations may cost as much as
  it saves; a size threshold would be needed so only larger buffers use DMA.
- SPI DMA would also require either cache clean/invalidate maintenance or
  non-cacheable DMA buffers before D-cache could be enabled safely.

For this reason DMA is classified as a CPU-utilization and large-payload
experiment, not an assumed 100-byte-stream throughput improvement. A useful
DMA trial must compare 100- and 1,472-byte packets at the same effective SPI
clock, report MCU active cycles, and demonstrate no latency or reliability
regression. It should be retained only if that measured benefit justifies the
additional DMA channels, interrupts, cache policy, and adapter code.

## Remaining offload optimization candidates

| Priority | Candidate | Expected benefit | Main tradeoff |
|---:|---|---|---|
| Done | Give SPI1 a dedicated clock while the CPU remains at 520 MHz | 40 MHz raised the clean sweep boundary from 12 to 14 kHz | 50 MHz failed DHCP in this combined configuration, so 40 MHz was retained |
| 1 | Enable D-cache only for W5500 offload while SPI remains CPU-driven | Lower CPU/data-access cost without native Ethernet DMA coherency problems | Must be reverted or supplemented with cache maintenance if SPI DMA is later added |
| 2 | Allocate 8 KiB W5500 RX/TX RAM to the echo socket and disable unused socket buffers | Better burst absorption and tolerance of short host scheduling stalls | Does not increase the sustained serial-bus service rate; DHCP/profiling sockets still need RAM |
| 3 | Reduce register transactions in a small, audited low-level UDP fast path | Higher small-packet rate by combining adjacent register reads and avoiding repeated pointer work | Duplicates some `w5500-hl` logic and raises maintenance/correctness risk |
| 4 | Tune W5500 `INTLEVEL` for interrupt coalescing | Fewer wakeups at high packet rates | Intentionally adds receive latency, so it is a poor default for the 1 kHz control workload |
| 5 | Use DMA only above a measured payload-size threshold | Lower MCU active cycles and possibly better large-packet transfer efficiency | High integration complexity and little expected benefit for short register transactions |

The dedicated SPI clock experiment is complete: 50 MHz did not pass DHCP in
combination with the 520 MHz CPU, while 40 MHz passed and materially improved
the stream result. D-cache is now the next-lowest-complexity experiment.
Socket RAM allocation should be evaluated with the burst test rather than
judged only by the sustained 100-byte stream.
